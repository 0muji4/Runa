# DD: きょうの一曲を実在の楽曲の紹介と試聴にする

Status: Finalized
PRD: [きょうの一曲を実在の楽曲の紹介と試聴にする](../prd/todays-song-itunes-preview.md)

## 背景

PRD は、きょうの一曲を Apple のカタログの楽曲の紹介と 30 秒の試聴にすることを求めている。本 DD が答える問いは、「運営者が登録した Apple の楽曲の識別子から、Apple の宣伝目的の条件を満たす形で、両 OS の 07/08 画面に紹介と試聴を届けるには、サーバーとクライアントのどこを変えるか」である。

前提とする現状は次のとおりである。

- サーバーは `daily_songs` に日付ごとの曲を持ち、`GET /api/v1/today` と `GET /api/v1/songs` がその行をそのまま返す。行は曲名・アーティスト名・`artwork_url`・`audio_url` を持つ（マイグレーション 0004）。
- 登録は `POST /api/v1/admin/songs` に運営者が四つの値を直接入れる。
- クライアントは shared の `SongDto` を受け取り、`audioUrl` を `AudioPlayer`（Android は ExoPlayer、iOS は AVPlayer）に渡してストリーミング再生する。`SongPlayerViewModel` が再生・一時停止・シークを持ち、新しい曲の再生開始で `POST /songs/{id}/played` を記録する。
- ホームは `/today` の応答を SQLDelight にキャッシュし、オフラインでも直近の曲名などを表示する。

## 概要

結論は、**楽曲の識別子（iTunes の trackId）だけを正とし、Apple から取得した楽曲情報（曲名・アーティスト名と、アートワーク・試聴・ストアリンクの各 URL）をサーバーの行に保存し、保存してから時間が経ったら読み出しの応答を待たせず、バックグラウンドで取得し直す**である。クライアントは Apple を知らず、サーバーから受け取った楽曲情報を表示・再生するだけにする。

この方向になる理由は二つある。第一に、PRD の N4（利用者数に比例して Apple への問い合わせを増やさない）と N3（Apple が応答しなくても表示できる）は、取得をサーバーに集約し、結果を保存しておかないと満たせない。第二に、Apple の試聴 URL は恒久に同じであると保証されていないため、登録時に取得した楽曲情報を二度と更新しないと、URL が変わったとき運営者が気づくまで試聴が壊れる。

本 DD が設計判断を照らす要件は、PRD から次のとおり立てる。

- R1: 運営者は識別子と日付だけで登録でき、存在しない・試聴のない楽曲は登録時に失敗する（Step 1）
- R2: 07 で紹介（バッジを主）と試聴（再生・一時停止・進み具合、30 秒の表示）を見られる（Step 2）
- R3: 08 で過去の曲を新しい順に、R2 と同じ形で見られ、再生の記録は残る（Step 3）
- N1: アートワーク・試聴のある画面にバッジと帰属表示を置く
- N2: 試聴の音声を保存・キャッシュしない
- N3: Apple が応答しなくても直近の内容で表示できる
- N4: Apple への問い合わせが目安を超えず、利用者数に比例しない

論点は Q1 から Q5 で、それぞれ一つの要件群に対応する。順序は PRD と同じく、登録（Q1, Q2）から表示（Q3, Q4）へ進み、最後に運営の導線（Q5）を置く。

## 全体設計

変わるのは、サーバーの登録経路と行の中身、クライアントの契約と 07/08 画面である。`/today`・`/songs`・`/songs/{id}/played` の経路と、クライアントの再生機構、再生の記録は変わらない。

```
[運営者]                                   [Apple: iTunes Search API]
   │ POST /admin/songs {date, itunes_track_id}        ▲
   ▼                                                 │ lookup?id=…&country=jp
[API サーバー] ── TodayService ── itunes.Client ──────┘
   │                 │
   │                 ▼
   │           daily_songs（itunes_track_id + 楽曲情報 + resolved_at）
   │                 │
   │  GET /today, GET /songs（保存した楽曲情報を返す。古ければバックグラウンドで取得し直す）
   ▼
[Android / iOS] ── SongDto{title, artist, artwork_url, preview_url, store_url}
   ├─ 07/08: アートワーク・曲名・バッジ(store_url)・帰属表示
   └─ AudioPlayer(preview_url) をストリーミング再生（保存しない）
```

現在との差分は次の三点である。

1. `daily_songs` の正が「運営者が入れた四つの URL・文字列」から「`itunes_track_id`」に変わり、他の列は Apple から取得した楽曲情報になる。
2. サーバーに Apple を呼ぶ `itunes` パッケージが増え、登録時と楽曲情報の更新時に使う。
3. クライアントの `SongDto` から `audio_url` が消え、`preview_url` と `store_url` が入る。07/08 はバッジと帰属表示を持ち、シークを持たない。

## 詳細設計

### Q1: 楽曲をどう同定し、誰が Apple から取得するか（R1, N4）

**アプローチ**: 運営者の入力を一つの識別子に絞り、その識別子から Apple の情報を引く責務をどこに置くかを決める。

**設計**: 識別子は iTunes Search API の `trackId`（整数）とし、`daily_songs.itunes_track_id BIGINT NOT NULL` に持つ。サーバーの `internal/itunes` パッケージが `https://itunes.apple.com/lookup?id=<ids>&country=jp&entity=song` を呼び、応答の `results` から `kind == "song"` の要素を取り出す。取り出す項目と行の列の対応は次のとおりである。

| Apple の応答 | `daily_songs` の列 |
|---|---|
| `trackName` | `title` |
| `artistName` | `artist` |
| `artworkUrl100` | `artwork_url`（`100x100bb` を `600x600bb` に書き換え、HEAD で 200 を確認できたらその URL、できなければ元の URL を保存） |
| `previewUrl` | `preview_url` |
| `trackViewUrl` | `store_url` |

`results` が空、または `previewUrl` が空のときは、それぞれ `itunes.ErrNotFound` / `itunes.ErrNoPreview` を返す。`POST /admin/songs` は本文を `{date, itunes_track_id}` に変え、`TodayService.CreateSong` が登録前に lookup を呼び、取得できた楽曲情報だけを行にする。`ErrNotFound` / `ErrNoPreview` は 422 として理由つきで運営者に返し、ネットワークや 5xx は 502 として返す。

`itunes.Client` は `http.Client{Timeout: 5s}` を持ち、`oidc.go` の JWKS 取得と同じ作りにする。`country` は `jp` に固定する（Runa は日本向けで、他国のカタログを使う要件がない）。

応答の各 URL は `https` のものだけを受け取り、それ以外は空として扱う（試聴が空なら登録は `ErrNoPreview` になる）。クライアントは `store_url` を OS に渡して開き、`preview_url` をそのまま再生するので、スキームはサーバーで固定する。

アートワークについて、Apple の応答にある最大の解像度は 100px で、07 の大きさ（画面幅いっぱい、3 倍密度の端末で 1000px 前後）では足りない。`artworkUrl100` の `100x100bb` を `600x600bb` に書き換えると同じ CDN が 600px を返すことは広く知られているが、Apple の文書には無い。そこで書き換えた URL に HEAD を送り、200 が返ったときだけその URL を保存し、返らなければ元の 100px の URL を保存する。Apple が 600px を返さなくなった場合、表示はぼやけるが壊れない。

**根拠**: 運営者の入力を識別子だけにすると、曲名やアートワークの手入力の誤りが起きず、Apple に存在しない曲や試聴のない曲は登録時に検出できる（R1）。取得をサーバーに集約すると、Apple への問い合わせは登録と楽曲情報の更新のときだけになり、利用者数に比例しない（N4）。

**棄却案**:

- クライアントが `trackId` を受け取り、各端末が Apple を直接呼ぶ。利用者数に比例して Apple への問い合わせが増え、N4 に反する。バッジや帰属表示の規則が両 OS に分散し、Apple の変更に両方を追従させることになる。
- 運営者が Apple の各 URL を手で入力する（現状の延長）。試聴のない曲や存在しない曲を登録時に検出できず、R1 に反する。URL が変わったときに直す手段が運営者の目視だけになる。

### Q2: 保存した楽曲情報をいつ取得し直すか（N3, N4）

**アプローチ**: 試聴 URL が恒久でないという制約と、Apple が応答しなくても表示を続ける要件を、同時に満たす更新の時期を決める。

**設計**: 行に `resolved_at TIMESTAMPTZ NOT NULL` を持ち、`GET /today` と `GET /songs` が行を返すとき、`resolved_at` が 24 時間より古い行の楽曲情報をバックグラウンドで取得し直す。取得し直す間、応答は待たせない（応答には保存済みの楽曲情報を返す）。同じ曲の取得はプロセス内で一度に一つだけ走らせ、失敗した曲は 5 分間は再試行しない（取得中・失敗直後の曲をプロセス内の表で覚えておく）。`GET /songs` の一ページに古い行が複数あれば、`lookup?id=a,b,c` の一回でまとめて取得する。取得に成功したら楽曲情報の全列と `resolved_at` を更新し、失敗したら何もせずログに残す。取得し直しで 600px の確認だけが通らず 100px の URL が返ったとき（保存済みの URL がその 600px 版のとき）は、保存済みのアートワークを保つ。CDN の一時的な失敗で画面が 1 日ぼやけるのを避けるためである。

登録時の lookup が成功しないと行が作られないので、`resolved_at` と楽曲情報の列は常に値を持つ。

**根拠**: 取得し直す処理をバックグラウンドで行い、失敗しても保存済みの楽曲情報を返すので、Apple が応答しなくても直近の内容で表示できる（N3）。一曲あたり 24 時間に一度・失敗時は 5 分間隔なので、問い合わせ回数は「その日に読まれた曲の種類数」で抑えられ、利用者数に比例しない（N4）。

**棄却案**:

- 読み出しのたびに Apple を呼ぶ。Apple の応答がホームの表示の前提になり、N3 に反する。ホームを開くたびに問い合わせが起きて N4 にも反する。
- 登録時に一度だけ取り、二度と取得し直さない。試聴 URL が変わったとき、運営者が気づいて登録し直すまで試聴が壊れる。N3 は満たすが、恒久でない URL を恒久として扱っている。
- 定期実行（cron）で全行を取得し直す。行数に比例して問い合わせが起き、読まれない古い曲まで取得し直す。Runa には定期実行の基盤がまだなく、そのためだけに基盤を足すことになる。読み出し時に取得し直せば足りる。

### Q3: クライアントとの契約をどう変えるか（R2, R3, N2）

**アプローチ**: 試聴が 30 秒のプレビューであることと、ストアリンクが必須であることを、契約の名前と型で表す。

**設計**: `Song` の応答（`/today` の `song`、`/songs` の各要素）を次にする。

```json
{
  "id": "…", "date": "2026-09-13",
  "title": "…", "artist": "…",
  "artwork_url": "https://…/600x600bb.jpg",
  "preview_url": "https://…/preview.m4a",
  "store_url": "https://music.apple.com/jp/album/…?i=…"
}
```

`audio_url` は削除し、`preview_url` に置き換える。`itunes_track_id` と `resolved_at` はクライアントに返さない（表示にも再生にも使わない）。shared の `SongDto` と SQLDelight の曲テーブルを同じ形にし、`openapi.yaml` を更新する。

`GET /songs` には `until`（クライアントの現地日、YYYY-MM-DD）を足し、その日以前の曲だけを返す。運営者は先の日付まで登録しておくので、絞らないと「これまでの一曲」に明日以降の曲が並ぶ。省略時はサーバーの UTC 日。

`preview_url` は `AudioPlayer.load` にそのまま渡す。ExoPlayer は `CacheDataSource` を使っておらず、AVPlayer はストリーミング再生のみなので、音声はどちらの OS でもディスクに残らない。この状態を保つことを `AudioPlayer` の doc コメントに明記する。アートワークは Coil / `AsyncImage` の既定のキャッシュのままでよい（N2 の対象外）。

**根拠**: 名前を `preview_url` にすると、クライアントの実装者がこれを全曲の音源として扱う余地がなくなる。`store_url` を必須の列にすると、バッジの無い画面が作れない（N1 の前提）。音声のキャッシュを足さないことを契約の側に書くことで、N2 が両 OS の実装に残る。

**棄却案**:

- `audio_url` の名前を残す。互換のための利点はない（クライアントは同じリポジトリで同時に更新する）。名前が実態と食い違い、将来の読み手が「フルの音源」と誤読する。

### Q4: 07/08 画面に何を置き、何を置かないか（R2, R3, N1）

**アプローチ**: Apple の六条件のうち画面に現れる 1〜3 と 5 を、画面の要素として固定する。

**設計**: 07 きょうの一曲と 08 これまでの一曲の各曲は、次の要素を持つ。

- アートワーク、曲名、アーティスト名（現状どおり）
- Apple の公式バッジ「Apple Music で聴く」。タップで `store_url` を OS の既定の方法で開く（Android は `ACTION_VIEW`、iOS は `openURL`。Apple Music アプリがあればそちらが開く）。バッジの画像は Apple の公式素材を使い、自作しない。
- 試聴の再生・一時停止ボタンと、進み具合の表示（操作できない）。ボタンの近くに「30 秒の試聴」と示す。
- 帰属表示 "provided courtesy of iTunes"（この文言のまま）

07 はバッジを試聴より上に置き、視線の主にする。シークバーは置かず、`SongPlayerViewModel.seekTo` と `AudioPlayer.seekTo` は削除する（呼び出し元がなくなる）。08 は一覧の各行にバッジを置き、帰属表示は一覧の先頭に一つ置く（N1 は画面単位で求められる）。08 の「再生の記録」は曲名とアーティスト名の文字だけにし、アートワークを出さない。アートワークもバッジの隣にしか置けない Promo Content であり、記録の行にバッジを並べる理由がないためである。これに合わせて、端末の再生記録（SQLDelight の `song_history`）からアートワークの列を落とす。

再生の記録は現状どおり、新しい曲の再生開始で `POST /songs/{id}/played` を送る。

**根拠**: バッジ・帰属表示・「その曲の画面にだけ置く」は Apple の条件 1〜3 の直訳で、N1 を満たす。バッジを主に置き、シークを持たない試聴を補助に置くことで、条件 5（独立した娯楽価値）に読まれにくくする。R2/R3 の要素はこれで尽きる。

**棄却案**:

- シークバーを残す。Apple の条件は禁じていないが、30 秒の中を行き来する操作は試聴をプレイヤーの体験に寄せる。残す利点が無い。
- 帰属表示を設定画面などにまとめて置く。条件 3 は「プレビューを含む Promo Content に帰属表示を含める」と求めており、同じ画面に置くのが素直な読みである。別画面にまとめると条件を満たすかの判断が読み手に委ねられる。

### Q5: 運営者の登録の導線をどう作るか（R1）

**アプローチ**: 運営者が `trackId` を見つける手段と、日付に登録する手段を用意する。

**設計**: `hack/itunes-search.sh <検索語>` を足し、`https://itunes.apple.com/search?term=…&country=jp&entity=song&limit=10` の結果を `trackId / 曲名 / アーティスト名 / 試聴の有無` の一覧で表示する。`hack/seed-today.sh` は日付と `trackId` の組を `POST /admin/songs` に送る形に変え、運営者が用意した音源の URL は使わない。

**根拠**: 検索は認証不要の公開 API で、運営者がブラウザで行っても同じ結果になる。スクリプトにするのは `trackId` を目で拾う手間を省くためだけで、サーバーに検索の口を足す必要はない（R1 は登録だけを求めている）。

**棄却案**:

- サーバーに `GET /admin/songs/search` を足す。登録経路が二つになり、認証つきの口を運営者専用の検索のために増やすことになる。運営の頻度（日に一曲）に対して過剰である。

## マイグレーション

0007 として次を行う（0006 は通知デバイス登録が使っている）。

1. `daily_songs` の全行を削除する（既存の行は Apple の識別子を持たず、楽曲情報を取得できない。PRD Step 1）。`song_history` は `ON DELETE CASCADE` で消える。
2. `itunes_track_id BIGINT NOT NULL`、`store_url TEXT NOT NULL`、`resolved_at TIMESTAMPTZ NOT NULL` を足し、`audio_url` を `preview_url` に改名する。

SQLDelight は `1.sqm`（スキーマ 1 → 2）で `today_song` と `song_history` を作り直す。どちらも端末のキャッシュと記録なので列ごとの移行はせず、曲は次回の `/today` 取得で埋まり、再生の記録は空から始まる。

## 障害シナリオとエッジケース

| 場面 | 振る舞い |
|---|---|
| 登録時に Apple が 5xx / タイムアウト | 行を作らず 502 を返す。運営者が再試行する |
| 登録時に該当曲なし・試聴なし | 行を作らず 422 を返す（理由を本文に入れる） |
| 取得し直すときに Apple が応答しない | 保存済みの楽曲情報を返し、5 分は再試行しない。ログに残す |
| 楽曲情報は新しいが `preview_url` の先の音声が消えている | クライアントの再生が失敗し、既存の再生エラー表示になる。次に取得し直したとき（最長 24 時間後）に直る |
| 端末がオフライン | SQLDelight に保存した楽曲情報で 07/08 を表示する。試聴は既存のオフライン表示になる |
| 同じ曲を別の日に登録 | `itunes_track_id` に一意制約は置かない。`date` の一意制約は現状どおり |

## 将来の拡張

- Apple Music 加入者向けのフル再生（MusicKit）を足すとき、`itunes_track_id` は Apple Music API の catalog id と同じ値なので、行の識別子はそのまま使える。
- Apple が iTunes Search API を廃止したら、`itunes` パッケージだけを別の取得元（Apple Music API の catalog lookup）に差し替える。契約と画面は変わらない。
