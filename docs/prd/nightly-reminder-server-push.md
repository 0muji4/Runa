# PRD: 今日の記録が無い夜だけ、サーバーからリマインドを届ける

Status: Finalized

## 背景と課題

夜のリマインドを、「その日の記録がまだ無いときだけ届く」通知にする。

Runa は夜に寄り添う日記アプリで、記録の主体は利用者である。利用者が選んだ夜の時刻に「月が出ました / 今日を、そっと綴りませんか。」と知らせる「夜のリマインド」（21 通知設定）は、今日を書き残す合図として置かれている。

現在のリマインドは端末のローカル通知である。Android は `AlarmManager`、iOS は `UNCalendarNotificationTrigger` が、設定した時刻に毎晩同じ通知を出す。ローカル通知はサーバーを要さずオフラインでも鳴るが、**書いたかどうかに関係なく鳴る**。すでに今日を綴った利用者にも「綴りませんか」と届くので、合図が合図として機能しない。

「書いたか」を通知の時点で判定するには、その日の記録の有無を知っている場所で判定する必要がある。端末のローカル通知は、iOS では発火時にアプリのコードが走らないため判定を挟めない。また、利用者は複数の端末（iPhone と Android など）を持ちうる。ある端末で書いた記録は、同期を通じてサーバーには届くが、他の端末のローカル通知はそれを知らない。全端末の記録を知っているのはサーバーだけであり、判定はサーバーに置くしかない。したがって、リマインドはサーバーが判定して送る通知（プッシュ通知）にする。

## 要件

### Step 1: 利用者の端末は、リマインドを受け取る先としてサーバーに登録される

利用者がサインインしている端末は、プッシュ通知の宛先（OS が発行するトークン）と、その端末で選んだリマインドの設定（ON/OFF と時刻）、端末のタイムゾーンをサーバーに登録する。登録は利用者の操作を要さず、設定を変えたとき・トークンが変わったとき・タイムゾーンが変わったときに自動で更新される。

設定は端末ごとに持つ。iPhone で ON にしても Android はその端末の設定に従う。21 通知設定の画面が示す値は、常にその端末の登録内容と一致する。

サインアウトした端末とアカウントを削除した利用者の端末は、登録から外れる。

### Step 2: 選んだ時刻に、その日の記録が無いときだけリマインドが届く

利用者が選んだ時刻（21 通知設定。既定 22:00）に、サーバーはその利用者がその日（端末のタイムゾーンでの暦日）に記録を持つかを調べ、持たないときだけ、登録された端末にリマインドを送る。文言は現在と同じ「月が出ました / 今日を、そっと綴りませんか。」である。

すでに記録があるときは何も届かない。記録は利用者のどの端末で書いたものでもよい。

通知の本文に日記の内容は含めない。

### Step 3: 届いたリマインドをタップすると、新しい記録を書く画面が開く

利用者がリマインドをタップすると、アプリが開き、新しい日記を書く画面（10 ダイアリー作成）が表示される。プライバシー・ロック（22）が ON の端末では、ロック解除の後に表示される。サインインしていない端末では、サインイン画面が表示され、記録の画面へは進まない。

### 非機能要件

- N1（一日一回）: 同じ端末に、同じ日のリマインドは一回しか届かない。サーバーやネットワークの障害で送り直しが起きても、二回目は届かない。
- N2（時刻の精度）: リマインドは、選んだ時刻から 1 時間以内に届くか、その夜は届かない。1 時間を過ぎた夜のリマインドは、翌朝や深夜に届いてはならない。
- N3（内容の秘匿）: 通知の本文と、サーバーが通知の配送に使う外部サービスに渡す内容に、日記の本文・気分・画像を含めない。
- N4（届けない対象）: リマインドを OFF にした端末、サインアウトした端末、アカウントを削除した利用者の端末、OS が無効と判定したトークンには届けない。利用者が操作せずにサインインが切れた端末（強制サインアウト）については、端末が再登録しなくなってから一定期間（45 日）で対象から外れることを許容する。
- N5（運用費）: 現在の構成（Render 無料プラン・Neon 無料プラン）の枠内で運用でき、月額の追加費用が生じない。

## 責務の境界

利用者の端末は、宛先の登録と、届いた通知の表示・タップ後の遷移を担う。サーバーは、送るか送らないかの判定、送る時刻の管理、外部の配送サービス（Apple と Google のプッシュ通知基盤）への送信を担う。配送サービスから端末への到達は配送サービスの責務であり、Runa は到達を保証しない。

以下は Runa の責務の外に置く。

- Google Play サービスを持たない Android 端末（プッシュ通知の基盤が無い）
- 端末メーカー独自の省電力機能でアプリが強制終了された端末
- Apple / Google の配送サービスの障害

## リスクと前提条件

前提条件:

- Apple Developer Program と Firebase（Google）のプロジェクトを運営者が用意し、それぞれの配送サービスの認証情報をサーバーに設定すること。手順は運用手順書（`docs/runbook/push-notification-setup.md`）が扱う。
- 端末が同期でサーバーに記録を送っていること。オフラインで書いた記録は同期されるまでサーバーに無いので、その間にリマインドの時刻が来ると届きうる。Android は端末に当日の記録があれば表示しないことで補う。iOS ではこの場合に届くことを許容する。

リスク:

- サーバー起点になることで、ローカル通知には無かった「届かない」障害が生じる（認証情報の失効、サーバーの停止、配送サービスの障害）。どの障害がどの範囲に影響し、どう気づくかは DD が扱う。
- 現在のローカル通知は、この変更でなくなる。サーバーが送れない状況では、以前なら鳴っていたリマインドが鳴らない。この後退は「書いたのに鳴る」を無くすことと引き換えに受け入れる。

## 今後扱う範囲（別ドキュメント）

- 「今日の言葉」「きょうの一曲」が公開されたことの通知、うつろい（16）の手紙が読めるようになったことの通知。今回の登録の仕組みはそのまま使える。
- リマインドの設定を利用者単位（全端末共通）にすること。
- 通知が開かれた回数の計測。
